## Why software engineers (SWE) do not actively use TM Forum artifacts

- TM Forum artifacts are widely perceived as architecture-level assets. In most projects this perception is accurate, since architects or solution designers are responsible for defining external interfaces, not developers.

- TMF Open API artifacts are often seen as overly complex, highly abstract, and overengineered. They provide limited immediate value for software engineers, while their benefits are mostly long term and typically fall under the responsibility of architects rather than delivery teams.

- As a telecom operator, we usually focus on a limited set of use cases at any given time. As a result, we rarely need the full breadth of TMF Open API capabilities. For software vendors, these artifacts are more critical because they must support many different use cases across diverse customers.

- IDE and developer-tooling support for TMF artifacts is weak, which makes day-to-day usage inconvenient for software engineers.

- Many developers are not sufficiently aware of which TMF artifacts exist or how to use them effectively in their daily work.

- The ecosystem relies heavily on PDF documentation, with only a small number of automated tools available for governance, validation, and integration into development workflows.

- The documentation volume is very high: an Open API specification typically spans 100–150 pages, while the TMF Open API guidelines add another 250–300 pages.

- Overall, TMF documentation imposes a high cognitive load. The materials are usually very large and not tailored to a software-engineer-centric perspective.
